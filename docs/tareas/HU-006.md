## 2. Objetivo
Cada merge a `develop` con CI en verde aplica las migraciones en el Supabase de Staging y, solo si salen bien, despliega la versión nueva en Render; un fallo de migración o de salud deja la versión anterior sirviendo. Producción tiene un flujo con aprobación manual listo pero inactivo, y existe un procedimiento de rollback probado en Staging.

**Definición exacta del job `desplegar-staging`** (usar tal cual, con la CLI fijada en `2.116.0` (D-109)):

```yaml
  desplegar-staging:
    if: ${{ github.event_name == 'push' && github.ref == 'refs/heads/develop' }}
    needs: [build-y-pruebas, secretos, sql, conventional-commits]
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    environment: staging
    concurrency:
      group: despliegue-staging
      cancel-in-progress: false
    steps:
      - uses: actions/checkout@v4
      - uses: supabase/setup-cli@v1
        with:
          version: 2.116.0
      - name: Aplicar migraciones en Staging
        env:
          DB_URL: ${{ secrets.DB_URL }}
        run: |
          set -euo pipefail
          echo "::add-mask::$DB_URL"
          supabase db push --db-url "$DB_URL"
      - name: Disparar el despliegue en Render
        env:
          RENDER_DEPLOY_HOOK: ${{ secrets.RENDER_DEPLOY_HOOK }}
        run: |
          set -euo pipefail
          echo "::add-mask::$RENDER_DEPLOY_HOOK"
          curl -fsS -X POST "$RENDER_DEPLOY_HOOK" >/dev/null
      - name: Verificar salud tras el despliegue
        env:
          URL_BASE: ${{ vars.URL_BASE }}
        run: |
          set -euo pipefail
          sleep 90
          for intento in $(seq 1 40); do
            if curl -fsS "$URL_BASE/health/ready" >/dev/null && curl -fsS "$URL_BASE/api/v1/estado" >/dev/null; then
              echo "OK: Staging responde"; exit 0
            fi
            sleep 15
          done
          echo "ERROR: Staging no quedo sano a tiempo"; exit 1
```

## 6. Prohibiciones (se revisan al pie de la letra)
- No escribir secretos, URLs de conexión, deploy hooks, contraseñas ni tokens en ningún archivo versionado; solo sus **nombres**. Los valores van en los entornos de GitHub y en el panel de Render.
- No usar `pull_request_target`. El job de despliegue corre solo con `push` a `develop` o con `workflow_dispatch` desde `main`; nunca con eventos de PR (el repositorio es público: los forks no deben alcanzar los secretos).
- No usar `continue-on-error`, `if: always()` ni `if: failure()` en los pasos de migración o de disparo del despliegue (E3).
- No ampliar `permissions` del workflow (se mantiene `contents: read`).
- No usar acciones de terceros distintas de `actions/checkout@v4` y `supabase/setup-cli@v1`; sin `latest` en la versión de la CLI.
- No usar DELETE ni nombres de método de eliminación; no crear migraciones "down".
- No tocar `AGENTS.md`, `CLAUDE.md`, `Directory.*.props` ni `src/`. Los cambios de `.github/` son solo los listados en 4.1.
- **Commits:** Conventional Commits con asunto en ASCII (sin acentos ni eñes) y de 72 caracteres o menos; confirmar **por ruta**, nunca `git add .`. Valida con `python3 scripts/ci/validar_conventional_commits.py --base develop`. Sin push.
