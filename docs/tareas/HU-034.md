## 2. Objetivo
Entregar el mecanismo que ejecuta tareas programadas dentro del mismo host (ADR-11): `BackgroundService` + tablas `app.tareas` y `app.tareas_ejecuciones` + reserva atómica en PostgreSQL para que, con varias instancias, cada tarea corra en una sola a la vez. Incluye reintentos, tiempo máximo y registro de inicio, fin y resultado. **Este ejecutor no trae tareas de negocio**: la cola de correo (HU-010) y las publicaciones programadas (HU-049) se enchufan después implementando `ITareaProgramada`.

```csharp
public sealed record TareaReservada(string Nombre, string Programacion, int TimeoutSeg, int MaxReintentos);

Task<TareaReservada?> ReservarSiguienteAsync(DateTime ahoraUtc, int margenReservaSeg, CancellationToken cancelacion = default);
Task RenovarReservaAsync(string tareaNombre, DateTime hastaUtc, CancellationToken cancelacion = default);   // R-2: extiende la reserva (lease) mientras la tarea sigue en curso
Task<long> IniciarEjecucionAsync(string tareaNombre, DateTime inicioUtc, string instancia, CancellationToken cancelacion = default);
Task FinalizarEjecucionAsync(long ejecucionId, DateTime finUtc, ResultadoEjecucion resultado, string? error, CancellationToken cancelacion = default);
Task ProgramarSiguienteAsync(string tareaNombre, DateTime ultimaEjecucionUtc, DateTime proximaEjecucionUtc, CancellationToken cancelacion = default);
Task<bool> HayTareasActivasAsync(CancellationToken cancelacion = default);   // opcional, solo si lo necesitas; si no, omítelo
```
`ReservarSiguienteAsync` es **una sola sentencia atómica** (SUP-3), ejecutada con `Database.SqlQuery<T>` y parámetros (nunca concatenar cadenas):
```sql
update app.tareas
   set proxima_ejecucion_utc = @ahora + make_interval(secs => timeout_seg * (max_reintentos + 1) + @margen)
 where nombre = (select nombre from app.tareas
                  where activa and (proxima_ejecucion_utc is null or proxima_ejecucion_utc <= @ahora)
                  order by proxima_ejecucion_utc nulls first, nombre
                  limit 1
                  for update skip locked)
returning nombre, programacion, timeout_seg, max_reintentos
```
La nueva `proxima_ejecucion_utc` es una **reserva (lease)**: mientras dure, ninguna otra instancia puede tomar la tarea; si la instancia muere, la reserva vence sola y otra la retoma. Los parámetros `DateTime` deben ser UTC (Npgsql `timestamptz`).

**`ServicioEjecutorTareas.EjecutarSiguienteAsync`:**
1. `ReservarSiguienteAsync(reloj.AhoraUtc, opciones.MargenReservaSegundos)`; si es `null`, devolver `false`.
2. Buscar el manejador por `Nombre` (comparación exacta). Si no hay manejador: registrar `LogError`, crear la ejecución y cerrarla como `Fallida` con error `SinManejador`, programar la siguiente y devolver `true` (SUP-5).
3. Si `ProgramacionTarea.TryObtenerIntervalo` falla: igual que el punto anterior con error `ProgramacionInvalida`, y reprogramar a `ahora + 1 hora` para no saturar los logs.
4. Intentos: `1 + MaxReintentos`. Por **cada intento**: `IniciarEjecucionAsync` (con `Instancia` = `Environment.MachineName` + `:` + id de proceso), ejecutar el manejador con un `CancellationTokenSource` enlazado al token del host y `CancelAfter(TimeoutSeg)`, y `FinalizarEjecucionAsync`:
   - Termina sin excepción → `Exitosa`, `error = null`, no hay más intentos.
   - `OperationCanceledException` por el timeout propio (no por apagado del host) → `Cancelada`, error `TiempoMaximoExcedido:<TimeoutSeg>s`; **no se reintenta** (SUP-7).
   - Cancelación por apagado del host → `Cancelada`, error `ApagadoDelServicio`, sin más intentos; relanzar la cancelación tras cerrar el registro.
   - Cualquier otra excepción → `Fallida`, error = **solo el nombre del tipo de la excepción** (SUP-8, sin mensaje ni datos sensibles; el detalle completo va a `LogError` con la excepción). Si quedan intentos, **antes de esperar** llamar a `RenovarReservaAsync(nombre, ahora + espera + TimeoutSeg + MargenReservaSegundos)` (R-2: la reserva inicial no cubre el retroceso exponencial), esperar `EsperaBaseReintentoSegundos * 2^(intento-1)` con `IEspera` y reintentar; si se agotan, el último registro queda `Fallida` y se escribe `LogWarning` "reintentos agotados".
5. Al terminar (cualquier resultado): `ProgramarSiguienteAsync(nombre, ultimaEjecucionUtc: inicio del primer intento, proximaEjecucionUtc: reloj.AhoraUtc + intervalo)`. Así la reserva termina y el siguiente ciclo respeta el intervalo.
6. Los fallos al escribir el registro no deben tragarse en silencio: si `FinalizarEjecucionAsync` lanza, registrar `LogError` y dejar que la reserva venza sola.
7. Todos los `DateTime` salen de `IRelojUtc`; nunca `DateTime.Now`/`UtcNow`.

**`EjecutorTareasHostedService`** (vive en `src/Nilogistic.Aplicacion/Tareas/EjecutorTareasHostedService.cs`, namespace `Nilogistic.Aplicacion.Tareas`; el host aloja el `BackgroundService` y solo ve la BLL y la Utility, nunca el DAL): recibe `IServiceScopeFactory`, `IOptions<OpcionesEjecutorTareas>`, `ILogger<>` e `IEspera`. Si `Habilitado = false`, termina de inmediato. En el bucle: crea un scope por iteración, resuelve `IServicioEjecutorTareas`, llama a `EjecutarSiguienteAsync` repetidamente mientras devuelva `true`, y si devuelve `false` espera `IntervaloSondeoSegundos` con `IEspera`. **Debe capturar toda excepción dentro del bucle** (excepto la cancelación del host), registrarla y seguir tras la espera: en .NET una excepción no controlada de un `BackgroundService` detiene el host. La conexión a la base no se mantiene abierta mientras espera.

## 11. Supuestos y decisiones que requieren aprobación de Jorge
| ID | Supuesto | Alternativa / riesgo |
|---|---|---|
| SUP-1 | **R1 soporta solo programación por intervalo** (`intervalo:<segundos>`), no cron. Las dos tareas de R1 (cola de correo y publicaciones programadas) son periódicas. Cron exigiría el paquete Cronos o código propio | La HU dice "intervalo o cron". Se difiere cron a la primera tarea de R2 que lo necesite (gracia, cierres), registrándolo como deuda. Es una desviación parcial de la HU: requiere tu visto bueno |
| SUP-2 | `Tarea` y `TareaEjecucion` **no heredan `EntidadBase`**, porque el modelo aprobado (Fase 5 B) define columnas propias y son infraestructura, no entidades de negocio | Heredar obligaría a añadir `id`, `creado_por`, etc. y soft delete a una tabla técnica. El historial no se borra de todos modos (sin DELETE) |
| SUP-3 | Exclusión entre instancias con **reserva atómica por fila** (`FOR UPDATE SKIP LOCKED` + lease en `proxima_ejecucion_utc`), no con advisory locks de sesión | ADR-11 admite ambas. La reserva por fila no mantiene conexiones abiertas (el pooler de Supabase es modo sesión con pool de 10) y se recupera sola si una instancia muere |
| SUP-4 | La HU no inserta filas en `app.tareas`; cada HU de negocio añade la suya por migración | Evita tareas sin manejador en Staging |
| SUP-5 | Una fila de `app.tareas` sin manejador registrado se registra como `Fallida` (`SinManejador`) y se reprograma | Alternativa: ignorarla en silencio. Preferimos el fallo visible (lo consumirá HU-035) |
